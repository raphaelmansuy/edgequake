## Analysis of Findings

### First Principles Assessment

The core issue is a **timing mismatch**:

1. Upload completes instantly → returns track_id
2. Frontend immediately polls for progress
3. Progress is only initialized when task processing begins (async, delayed)

### Solution Options

| Option                                       | Description                                                    | Pros                             | Cons                                         | Risk   |
| -------------------------------------------- | -------------------------------------------------------------- | -------------------------------- | -------------------------------------------- | ------ |
| **A: Initialize progress in upload handler** | Call `start_pdf_progress()` before returning                   | Immediate fix, no race condition | Slightly increases upload latency            | LOW    |
| **B: Return 200 with empty progress**        | Change progress endpoint to return empty struct instead of 404 | No upload handler changes        | Frontend needs to handle "not started" state | MEDIUM |
| **C: Use database-backed progress**          | Persist progress in PostgreSQL instead of in-memory            | Survives restarts                | More complex, over-engineering               | HIGH   |

### Recommended: Option A

**Rationale**: Initialize progress immediately in `upload_pdf_document()` before returning the response.

### Risk Assessment

| Risk                    | Likelihood | Impact | Mitigation                             |
| ----------------------- | ---------- | ------ | -------------------------------------- |
| Duplicate progress init | LOW        | LOW    | Use `entry()` API or idempotent insert |
| Progress never updated  | LOW        | MEDIUM | Task callback will update it           |
| Memory growth           | LOW        | LOW    | Cleanup on completion already exists   |

### Implementation Plan

1. In `upload_pdf_document()` (pdf_upload.rs):
   - After `create_pdf_processing_task()` returns task_id
   - Call `state.pipeline_state.start_pdf_progress(track_id, pdf_id, filename)`
   - This ensures progress exists before response is returned

2. The track_id to use:
   - If `options.track_id` is Some → use that
   - Else → need to determine what track_id is returned

Looking at the code, `track_id` in the response is `options.track_id` (from frontend), while `task_id` is generated by the task system. The progress endpoint uses `track_id` (user-provided), not `task_id`.
