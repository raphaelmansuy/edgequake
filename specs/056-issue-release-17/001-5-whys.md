# 5 Whys — Issue #300 Upload Stuck on Loading (v0.17.0)

## Symptom

After upgrading to **v0.17.0**, selecting a document starts upload but the UI remains on a loading / waiting state indefinitely, with no useful error.

## Why chain

### Why 1 — Why does the UI look stuck forever?

Because the WebUI keeps the upload/pipeline row in an **in-progress** state until it receives progress/completion events for the **`track_id` it subscribed to**.

`use-file-upload` calls `startTracking(uploadResult.track_id, …)` and retains rows with `status === "extracting"` until that track completes ([`use-file-upload.ts`](../../edgequake_webui/src/hooks/use-file-upload.ts)).

### Why 2 — Why does that `track_id` never receive progress?

Because progress is published under a **different id**.

For a UI-like upload we sent `track_id=ui_track_1784173469`. The API echoed that id in the response, but live progress advanced only under `task_id=pdf-71ab2f81-…`:

| Query | Result (v0.17.0 GHCR) |
|-------|------------------------|
| `GET /documents/pdf/progress/ui_track_…` | `overall_percentage=0`, all phases `pending` / “Waiting for Upload” |
| `GET /documents/pdf/progress/pdf-71ab2f81-…` | conversion pages advancing, then chunking/extraction |

### Why 3 — Why are there two IDs?

Because PDF enqueue always creates a **server** track id (`pdf-<uuid>`) while the WebUI also sends a **client** `track_id` for correlation.

Upload handler:

1. Enqueues with `enqueue.track_id = "pdf-…"`.
2. Calls `start_pdf_progress(effective_track_id)` where `effective_track_id` prefers the **client** id.
3. Returns `track_id: options.track_id` (client) and `task_id: enqueue.track_id` (server).

Pipeline callback then updates using **`self.task_id`** (server id only):

```195:201:edgequake/crates/edgequake-api/src/pipeline_progress_callback.rs
    pub fn complete_pdf_conversion_phase(&self) {
        let state = self.pipeline_state.clone();
        let track_id = self.task_id.clone();
        self.runtime_handle.spawn(async move {
            state
                .complete_pdf_phase(&track_id, PipelinePhase::PdfConversion)
                .await;
```

Same pattern in `on_extraction_start` (`start_pdf_progress(&track_id, …)` with `self.task_id`).

### Why 4 — Why did this become visible / painful in v0.17.0?

Because v0.17.0 made **Vision Ingest + real-time progress (SPEC-047 / SPEC-048 / SPEC-050)** the default UX path for PDFs:

- WebUI always uploads PDFs via `/documents/pdf` with `enable_vision: true` and a client `track_id`.
- Progress dialog / WS / SSE are first-class; a silent ID mismatch looks like “upload stuck” rather than “background job running”.
- Vision conversion is slower (seconds–minutes), so the stuck spinner is long-lived and easy to report as “broken forever”.

Backend processing itself is **not** dead: with Mistral we completed a 1-page vision PDF (`embedded_figure_sample.pdf` → 214 entities) while the client progress handle stayed at 0%.

### Why 5 — Why is there no error message?

Because from the API’s point of view nothing failed:

- HTTP upload returns **200** with `status: "queued"`.
- Document metadata under the **server** track advances (`converting` → `extracting` → `completed`).
- The client progress key exists but is simply never updated — polling returns an empty skeleton, not an error.

So the UI has no error channel to surface; it only has silence on the wrong key.

## Root statement (first principles)

**There is no single correlation ID across the upload response, progress store, and pipeline worker.**  
Client correlation ID ≠ worker task ID, and only the worker ID is updated. The product therefore appears hung while the system is actually working.

## Secondary findings (not the primary stuck-loader)

1. **`POST /api/v1/documents/upload` rejects `.pdf`** (`Allowed types: txt, md, …`). PDF must use `/documents/pdf`. Mis-routed clients get an immediate 400 (not infinite loading).
2. **Bootstrap LLM model vs env:** container had `EDGEQUAKE_LLM_MODEL=mistral-small-latest`, but health reported global LLM as `mistral-medium-3-5` while workspace/vision correctly used `mistral-small-latest`. Confusing, not the stuck loader.
3. **Migration notice:** health showed `latest_version: 86`, `migrations_applied: 85` on first boot — worth checking, unrelated to upload hang.
