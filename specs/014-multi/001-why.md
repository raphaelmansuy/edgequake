# SPEC-014 — WHY (Issue #236)

Issue: [#236](https://github.com/raphaelmansuy/edgequake/issues/236)

## Problem statement

Enterprise ingest flows need one request to carry many files. In code, EdgeQuake had:

- text batch upload endpoint implemented in routes (`/api/v1/documents/upload/batch`)
- no batch endpoint for PDF uploads
- batch endpoints not fully represented in OpenAPI docs

When API consumers rely on Swagger/OpenAPI as source-of-truth, "code exists but docs hide it" is equivalent to "feature missing".

## Why this matters

1. **Throughput** — one-request-per-file creates avoidable HTTP and auth overhead.
2. **Operational simplicity** — orchestration systems (Spring/ECS, jobs) need deterministic batch primitives.
3. **Contract trust** — if endpoint is in router but absent in OpenAPI, client generation and integration drift.
4. **Consistency** — text and PDF upload capabilities should be symmetric at API surface.

## Success criteria

- OpenAPI exposes both document and PDF batch upload routes.
- API accepts multiple files in one multipart request.
- Tenant/workspace scoping remains enforced.
- E2E proofs show:
  - Swagger displays both endpoints.
  - Multi-file text batch request succeeds.
  - Multi-file PDF batch request succeeds.
