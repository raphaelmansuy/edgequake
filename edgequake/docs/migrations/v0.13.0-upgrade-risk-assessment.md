# v0.13.0 Upgrade — Data Migration Risk Assessment

**Method:** First principles + code is law (migration SQL headers, `checksums.lock`, bootstrap behavior).  
**Baseline:** Last official release `v0.12.11` (2026-06-09).  
**Target:** `v0.13.0` — migrations **046–077** (32 new files; **066–077** carry DDL).

---

## Executive Summary

| Risk tier | Count | Operator action |
| --------- | ----- | ----------------- |
| **Low** (marker-only / additive DDL) | 046–065, 066 | Normal rolling restart |
| **Medium** (index rebuild / dedup at startup) | 068–075, 077 | Plan 2–5 min maintenance window on large DBs |
| **High** (none) | — | No destructive data migrations |

**Verdict:** Safe to upgrade with a **brief write lock** during startup migrations on databases with existing graph + vector data. No manual SQL required for greenfield or standard upgrades. Large production graphs (>100k vertices) should follow the staged rollout below.

---

## First-Principles Model

```
UpgradeRisk = f(DDL_type, graph_size, vector_count, concurrent_writers)
```

| DDL class | Blocking lock | Data loss | Reversible |
| --------- | ------------- | --------- | ---------- |
| Marker (`*_marker.sql`) | None | None | N/A |
| `ADD COLUMN IF NOT EXISTS` | Brief | None | Drop column |
| `CREATE TABLE IF NOT EXISTS` | Brief | None | Drop table |
| `DROP INDEX IF EXISTS` | Brief per index | None | Recreate index |
| `CREATE INDEX` (non-CONCURRENT) | SHARE (reads OK, writes blocked) | None | Drop index |
| `CREATE UNIQUE INDEX` + dedup | SHARE + dedup UPDATE | None if dedup succeeds | Manual |
| `CREATE OR REPLACE FUNCTION` | None | None | Drop function |

**Key insight:** sqlx runs migrations inside a transaction at **service startup**. PostgreSQL forbids `CREATE INDEX CONCURRENTLY` in transactions — therefore index-heavy migrations (071, 074) take a **SHARE lock** until complete. This is acceptable when no concurrent writers exist (single-instance startup); multi-instance rolling deploys should use **one instance first**.

## Deployment Scenarios

### A — Fresh install (Docker / `make dev`)

**Risk:** Minimal. All migrations apply on empty DB in <60 s.

```bash
make postgres-start && make backend-bg
curl http://localhost:8080/health | jq .schema
```

### B — Existing dev DB (v0.12.11 → v0.13.0)

**Risk:** Low–medium. Expect 1–3 min startup if vectors + graph populated.

1. Stop API: `make stop` or `pkill edgequake`
2. Pull / build new image or `cargo build --release`
3. Start single instance: `make backend-bg`
4. Watch logs: `grep -i migration /tmp/edgequake-backend.log`
5. Verify: `curl http://localhost:8080/ready`

### C — Production multi-instance

**Risk:** Medium if all instances restart simultaneously (migration advisory lock serializes, but second instance waits).

**Recommended:**

1. Scale API to **1 replica**
2. Deploy v0.13.0; wait for migrations + `/ready` 200
3. Scale remaining replicas
4. Monitor `edgequake.migration` logs and Postgres `pg_stat_activity`

### D — Large graph (>100k vertices)

**Risk:** Migrations 070/074 may take several minutes.

- `/ready` may return 503 during index build — expected
- Do **not** kill the process mid-migration (sqlx transaction rolls back)
- If startup exceeds SLA, contact ops for CONCURRENTLY playbook (future; not in sqlx path today)

## Pre-Upgrade Checklist

- [ ] Backup PostgreSQL (`pg_dump` or volume snapshot)
- [ ] Record current migration version: `SELECT version, description FROM _sqlx_migrations ORDER BY version DESC LIMIT 5;`
- [ ] Run checksum guard locally: `./scripts/check_migration_checksums.sh`
- [ ] Confirm disk headroom ≥ 2× largest HNSW index (071 rebuild needs temp space)
- [ ] Set maintenance window if DB has >10k vectors or >50k graph nodes
- [ ] Review auth env vars if upgrading from pre-SPEC-027 config

## Post-Upgrade Verification

```bash
# Migration version
psql "$DATABASE_URL" -c "SELECT max(version) FROM _sqlx_migrations;"

# Health
curl -fsS http://localhost:8080/health | jq '{status, schema}'

# Lineage tables exist
psql "$DATABASE_URL" -c "\d chunk_entity_links"

# HNSW ef_construction (expect 32 after 071)
psql "$DATABASE_URL" -c "SELECT indexdef FROM pg_indexes WHERE indexname LIKE '%hnsw%' LIMIT 1;"

# Re-ingest one document to populate lineage (066 backfill is lazy)
```

## Rollback Strategy

| Situation | Action |
| --------- | ------ |
| Migration fails mid-startup | Fix root cause; restart — sqlx retries pending migrations |
| App regression after upgrade | Deploy previous image **only if** migrations 066+ not yet applied |
| Migrations already applied | **Forward-fix only** — sqlx forbids downgrading applied checksums |
| Index performance regression (071) | Manual HNSW rebuild with `ef_construction=64` (see 071 header) |

**Critical:** Once `_sqlx_migrations` records 066+, rolling back the **binary** without restoring a **database snapshot** will cause schema/code mismatch.
